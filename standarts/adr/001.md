# ADR 001: Архітектура та стек технологій турнірної платформи

* **Cтатус:** Прийнято (Accepted)
* **Дата:** 10 жовтня 2026 р.
* **Автори:** Команда розробки турнірної платформи
* **Контекст проєкту:** Розробка високнавантаженої платформи для проведення кіберспортивних турнірів у середовищі IntelliJ IDEA.

---

## 1. Контекст та Проблема (Context & Problem Statement)

Необхідно спроектувати та реалізувати серверне забезпечення для турнірної платформи. Система повинна мати високу продуктивність, гарантувати цілісність даних при високій конкурентності (наприклад, масовий запис користувачів на останній слот турніру) та забезпечувати захист від дублювання транзакцій через нестабільне мережеве з'єднання.

Ключові вимоги:
1. Строга типізація бізнес-логіки та вхідних даних.
2. Легка підтримка та можливість майбутнього розщеплення на мікросервіси без переписання коду з нуля.
3. Гарантія ідемпотентності критичних операцій (наприклад, фіксація результатів матчів).
4. Захист від состояние гонки (Race Conditions) під час реєстрації учасників.

---

## 2. Архітектурне рішення: Модульний Моноліт (Modular Monolith)

### Decision
Замість передчасної розробки розподіленої мікросервісної архітектури обрано підхід **Modular Monolith**.

### Обґрунтування
* **Низька складність деплою та інфраструктури:** Моноліт розгортається як єдиний артефакт, що суттєво спрощує CI/CD та локальну розробку.
* **Чіткі межі контекстів (Bounded Contexts):** Проєкт розбивається на ізольовані доменні модулі (`registration`, `bracket`, `match`, `rules-engine`), кожен з яких має власні DTO, сервіси та маршрути.
* **Спільний модуль (`shared`):** Містить загальну інфраструктуру (Prisma Client, logger, idempotency middleware).
* **Готовність до мікросервісів:** У разі виникнення необхідності будь-який модуль може бути винесений в окремий сервіс за рахунок низької зв'язаності (Low Coupling).

## 3. Стек технологій (Technology Stack)

### 3.1. Core & Runtime
* **Node.js (LTS) & TypeScript:** Гарантують високу швидкість розробки та сувору статичну типізацію на всіх рівнях додатку.
* **Fastify:** Обрано замість Express через суттєво вищу продуктивність (низький overhead при обробці HTTP-запитів) та вбудовану підтримку схематичної валідації.

### 3.2. Валідація та Робота з Базою Даних
* **Zod:** Забезпечує runtime-валідацію входів (body, params, headers) із автоматичним виведенням TypeScript-типів.
* **PostgreSQL:** Надійна реляційна СУБД, що підтримує ACID-транзакції та транзакційне блокування рядків (`SELECT ... FOR UPDATE`).
* **Prisma ORM:** Сучасний інструмент для роботи з БД, що надає автозгенерований безпечний до типів клієнт (Type-safe Prisma Client) та зручну систему міграцій.

### 3.3. Тестування
* **Vitest:** Швидкий фреймворк для юніт- та інтеграційного тестування.
* **Playwright:** Інструмент для E2E-тестування API та сценаріїв користувача.

## 4. Ключові технічні рішення (Key Architectural Decisions)

### 4.1. Захист від Race Conditions (Конкурентний доступ)
При масовій одночасній реєстрації гравців на турнір виникає ризик перевищення доступних слотів (`maxSlots`).
* **Рішення:** Застосування транзакцій PostgreSQL із песимістичним блокуванням рядків або транзакційного перевірочного запиту в межах Prisma `$transaction`. Якщо кількість слотів вичерпана, транзакція відкочується (ROLLBACK) з поверненням помилки `TournamentFullException`.

### 4.2. Механізм Ідемпотентності (Idempotency Key)
Для уникнення подвійного збереження результатів матчів або повторного списання/нарахування балів через повторні HTTP-запити клієнта (через розрив зв'язку):
* **Рішення:** Реалізовано заголовок `X-Idempotency-Key` та окрему таблицю `idempotency_keys` в БД.
* **Алгоритм:**
  1. Сервер приймає запит із ключем.
  2. Якщо ключ вже існує зі статусом `COMPLETED`, повертається збережена відповідь без повторного виконання бізнес-логіки.
  3. Якщо ключ новий, створюється запис зі статусом `IN_PROGRESS`, виконується операція, оновлюється статус на `COMPLETED` і зберігається результат.

## 5. Наслідки (Consequences)

### Позитивні (Positive)
* Висока швидкість розробки та простота рефакторингу завдяки суворій типізації TypeScript + Prisma + Zod.
* Висока надійність даних при високих навантаженнях за рахунок транзакційності та ідемпотентності.
* Чиста та прозора структура проєкту.

### Негативні / Ризики (Negative / Risks)
* Монолітна база даних може стати пляшковим горлом (bottleneck) при масштабуванні до мільйонів користувачів (вирішується майбутнім шардингом або реплікацією читання).
* Потрібно суворо стежити за дотриманням меж модулів, щоб уникнути спагетті-коду між доменами.
