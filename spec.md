
# Специфікація системи: Настільно-Тенісна Турнірна Платформа

## 1. Архітектурний огляд

Система будується за принципом **Модульного Моноліту (Modular Monolith)** із застосуванням Layered Architecture.

### Доменні модулі

1. **RegistrationModule** — реєстрація користувачів, профілі, управління реєстраціями та кількістю вільних місць у турнірах.
2. **BracketModule** — алгоритми розподілу гравців (seeding) та побудови турнірної сітки (Single/Double Elimination).
3. **MatchModule** — проведення матчів, фіксація результатів, обробка конфліктів рахунку та захист від повторних запитів.
4. **RulesEngineModule** — перевірка правил настільного тенісу, включаючи гру до 11 очок та продовження гри при рахунку 10:10.

## 2. Межі модулів та міждоменна взаємодія

Для забезпечення ізоляції та запобігання циклічним залежностям:

- Модулі не звертаються безпосередньо до внутрішніх служб або баз даних інших модулів.
- Кожен модуль надає публічний сервісний інтерфейс (Service API / Facade).
- Міжмодульна взаємодія здійснюється через публічні DTO.
- Залежності передаються через Dependency Injection (DI).
- BracketModule отримує дані про зареєстрованих учасників через публічний інтерфейс RegistrationModule.
- MatchModule отримує інформацію про матч через власний сервісний інтерфейс.
- RulesEngineModule використовується MatchModule для перевірки коректності результатів.

## 3. Механізм Idempotency-Key

Для запобігання повторній обробці результатів матчу використовується заголовок `X-Idempotency-Key`.

### 3.1. Обробка запиту

Клієнт надсилає:

`POST /api/v1/matches/:id/score`

Заголовок:

`X-Idempotency-Key: <UUIDv4>`

### 3.2. Збереження ключа

Для кожного запиту створюється запис у таблиці `IdempotencyKeys` з полями:

- `key` — унікальний ідентифікатор запиту.
- `user_id` — користувач, який надіслав запит.
- `match_id` — матч, до якого належить запит.
- `response_payload` — збережена відповідь сервера.
- `status` — статус обробки (IN_PROGRESS або COMPLETED).
- `created_at` — дата створення.
- `expires_at` — час завершення терміну дії ключа.

Унікальність ключа забезпечується в межах користувача та запиту.

### 3.3. Повторні запити

- Якщо ключ має статус COMPLETED, повертається збережена відповідь без повторного виконання операції.
- Якщо ключ має статус IN_PROGRESS, повертається HTTP 409 Conflict.
- Якщо ключ відсутній, створюється новий запис зі статусом IN_PROGRESS.
- Після успішного збереження результату матчу запис переходить у статус COMPLETED.
- Запис ключа та зміна результату матчу мають виконуватися атомарно в межах транзакції.

## 4. Модель даних та зв'язки між сутностями

### 4.1. Users

Поля:
- `id`
- `email`
- `name`
- `created_at`

### 4.2. Tournaments

Поля:
- `id`
- `title`
- `max_players` — максимальна кількість учасників.
- `current_players` — поточна кількість зареєстрованих учасників.
- `status`
- `created_at`

Обмеження: `current_players` не може перевищувати `max_players`.

### 4.3. Registrations

Поля:
- `id`
- `tournament_id`
- `user_id`
- `registered_at`

Обмеження:
- `tournament_id` є зовнішнім ключем на Tournaments.id.
- `user_id` є зовнішнім ключем на Users.id.
- Комбінація `[tournament_id, user_id]` має бути унікальною.

### 4.4. Matches

Поля:
- `id`
- `tournament_id`
- `player1_id`
- `player2_id`
- `score_player1`
- `score_player2`
- `status`
- `round`

Зв'язки:
- `tournament_id` посилається на Tournaments.id.
- `player1_id` та `player2_id` посилаються на Users.id.
- Кожен матч належить одному турніру.
- Один турнір може містити багато матчів.

### 4.5. IdempotencyKeys

Поля:
- `key`
- `user_id`
- `match_id`
- `response_payload`
- `status`
- `created_at`
- `expires_at`

Зв'язки:
- `user_id` посилається на Users.id.
- `match_id` посилається на Matches.id.
- Один матч може мати декілька ключів ідемпотентності для різних запитів.
- Кожен ключ належить одному користувачу та одному матчу.

## 5. Сценарій конкурентної реєстрації

### 5.1. Проблема

Декілька користувачів одночасно намагаються зареєструватися на турнір, у якому залишилося одне вільне місце.

### 5.2. Рішення

Використовується транзакція бази даних та песимістичне блокування рядка турніру через `SELECT ... FOR UPDATE`.

Послідовність дій:

1. Заблокувати відповідний запис турніру.
2. Отримати значення `current_players` та `max_players`.
3. Перевірити, чи `current_players < max_players`.
4. Перевірити, чи користувач ще не зареєстрований.
5. Створити запис у Registrations.
6. Збільшити `current_players` на одиницю.
7. Підтвердити транзакцію.

Якщо місць немає, повернути помилку TournamentFullException та виконати ROLLBACK.

## 6. Критерії прийняття (Acceptance Criteria)

Система вважається такою, що відповідає специфікації, якщо виконуються наступні умови:

1. Кожен доменний модуль має визначену відповідальність та публічний інтерфейс.
2. Міжмодульна взаємодія відбувається через DTO та Facade.
3. Користувач не може зареєструватися на той самий турнір двічі.
4. Кількість зареєстрованих учасників не перевищує max_players.
5. При одночасній реєстрації на останнє місце успішно реєструється лише один користувач.
6. Повторний запит з тим самим X-Idempotency-Key не створює повторної операції.
7. Ключ ідемпотентності пов'язаний із конкретним матчем та користувачем.
8. Результат матчу проходить перевірку через RulesEngineModule.
9. Зв'язки між сутностями відповідають описаним зовнішнім ключам та обмеженням.

## 7. Обмеження та припущення

- Архітектура системи — модульний моноліт.
- Доступ до внутрішньої реалізації інших модулів заборонений.
- Операції реєстрації та оновлення результатів матчу мають бути транзакційними.
- Назви полів моделі даних повинні використовуватися послідовно в усіх розділах специфікації.
- Конкретна реалізація механізмів залежить від обраної технології зберігання даних.
