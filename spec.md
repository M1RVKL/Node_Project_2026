# Специфікація системи: Настільно-Тенісна Турнірна Платформа

## 1. Архітектурний огляд
Система будується за принципом **Модульного Моноліту** (Modular Monolith) із застосуванням **Layered Architecture** (Багатошарова архітектура з ізоляцією домену).

### Доменні модулі:
1. **RegistrationModule** — реєстрація користувачів, профілі, управління слотами турніру.
2. **BracketModule** — алгоритми розподілу (seeding) та побудови графової сітки (Single/Double Elimination).
3. **MatchModule** — фіксація результатів, обробка конфліктів рахунку, Idempotency-Key.
4. **RulesEngineModule** — валідація правил настільного тенісу (11 очок, баланс 10:10).

---

## 2. Межі модулів та міждоменна взаємодія

Для забезпечення ізоляції та запобігання циклічним залежностям:
- Модулі **НЕ звертаються** напряму до баз даних або внутрішніх служб інших модулів.
- Кожен модуль надає чіткий публічний сервісний інтерфейс (Service API / Facade).
- Взаємодія між `RegistrationModule` та `BracketModule` відбувається виключно через публічні DTO (Data Transfer Objects).
- `BracketModule` розроблений як повністю автономний модуль, підключений через **Dependency Injection (DI)**, що дозволить надалі безболісно винести його в окрему незалежну бібліотеку/сервіс при профілюванні навантаження.

## 3. Механізм Idempotency-Key (Захист від дублювання)

Для запобігання повторній відправці результатів матчу при затримках мережі у Модулі Проведення Матчів (`MatchModule`):

1. **Клієнтський запит:**
    - Клієнт надсилає `POST /api/v1/matches/:id/score` з заголовком `X-Idempotency-Key: <UUIDv4>`.
2. **Перевірка у базі / кеші:**
    - Перед відкриттям транзакції система перевіряє наявність `Idempotency-Key` у таблиці `idempotency_keys`.
    - Якщо ключ існує:
        - Якщо статус `COMPLETED` — повертається збережена відповідь (HTTP 200/201) без повторного виконання бізнес-логіки.
        - Якщо статус `IN_PROGRESS` — повертається помилка `409 Conflict` (запит уже обробляється).
    - Якщо ключ відсутній:
        - Створюється запис зі статусом `IN_PROGRESS` з таймаутом TTL.
3. **Обробка та завершення:**
    - Після успішного збереження рахунку статус запису змінюється на `COMPLETED`, а результатом запиту є кешована відповідь.

## 4. Модель даних та ER-зв'язки (Основні сутності)

- **Users**: `id`, `email`, `name`, `created_at`
- **Tournaments**: `id`, `title`, `max_players`, `status`, `created_at`
- **Registrations**: `id`, `tournament_id`, `user_id`, `registered_at` (Унікальний індекс по `[tournament_id, user_id]`)
- **Matches**: `id`, `tournament_id`, `player1_id`, `player2_id`, `score_player1`, `score_player2`, `status`, `round`
- **IdempotencyKeys**: `key`, `user_id`, `response_payload`, `status`, `created_at`

## 5. Сценарії оновлення даних при конкурентному доступі

### Сценарій: Реєстрація на турнір з обмеженою кількістю місць (Race Condition Prevention)
1. **Проблема:** Двоє або більше гравців одночасно намагаються зайняти останнє вільне місце в турнірі.
2. **Рішення:**
    - Транзакція бази даних з рівнем ізоляції **`REPEATABLE READ`** або песимістичне блокування рядка турніру (`SELECT ... FOR UPDATE`).
    - Кроки транзакції:
        1. Заблокувати рядок турніру `SELECT current_slots, max_slots FROM tournaments WHERE id = :id FOR UPDATE`.
        2. Перевірити, чи `current_slots < max_slots`.
        3. Якщо так: виконати `INSERT INTO registrations` та `UPDATE tournaments SET current_slots = current_slots + 1`.
        4. Якщо місць немає: підняти виключення `TournamentFullException` та відкотити транзакцію (`ROLLBACK`).
