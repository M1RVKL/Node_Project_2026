# ADR 0003: Вибір реляційної СУБД (PostgreSQL)

## Status
Прийнято (Accepted)

## Context
Турнірна платформа оперує суворо структурованими даними: Турніри, Користувачі, Реєстрації, Матчі та Сети. Завдання вимагає коректної обробки конкурентного доступу (race conditions) при реєстрації гравців на турніри з обмеженою кількістю місць.

## Decision Drivers
* Здатність бази даних забезпечувати сувору цілісність зв'язків (3НФ).
* Підтримка надійних транзакцій з налаштовуваними рівнями ізоляції (наприклад, Serializable або використання блокувань `FOR UPDATE`).

## Considered Options

* **PostgreSQL (Обрано)**
  * *Плюси:* Повна підтримка складних реляційних зв'язків; потужні механізми конкурентного доступу (MVCC) та транзакцій; ідеальна сумісність з обраною ORM (Prisma). Також використовувалась у минулих проектах.
  * *Мінуси:* Вимагає чіткого попереднього проєктування схеми.
* **MongoDB**
  * *Плюси:* Гнучка схема.
  * *Мінуси:* Не підходить для жорстко структурованих транзакцій (як-от реєстрація на турнір з лімітами); високий ризик аномалій даних без реляційних обмежень.
* **MySQL**
  * *Плюси:* Швидка та популярна реляційна СУБД.
  * *Мінуси:* PostgreSQL пропонує кращу роботу з JSON (що може знадобитися для специфічних конфігурацій турнірів) та строгіший стандарт SQL. Також незнайома для команди.

## Decision
Ми обрали **PostgreSQL** як основну базу даних.

## Consequences
* **Позитивні:** Гарантована відсутність втрачених оновлень при паралельній реєстрації гравців; захист від невалідних станів сітки.
* **Негативні:** Будь-які зміни в структурі даних вимагатимуть створення та запуску міграцій.
