
# ADR 001: Архітектура та стек технологій турнірної платформи

- **Статус:** Прийнято (Accepted)
- **Дата:** 10 жовтня 2026 р.
- **Автори:** Кореняко Антон, Жмуденко Даніїл, Бєлов Владислав

## 1. Контекст та проблема (Context & Problem Statement)

Необхідно спроєктувати серверну частину платформи для проведення турнірів з настільного тенісу.

Система повинна забезпечувати:
- цілісність даних під час одночасної реєстрації учасників;
- захист від повторної обробки HTTP-запитів;
- чітке розділення бізнес-логіки;
- можливість подальшого розширення системи;
- сувору типізацію бізнес-логіки та вхідних даних.

## 2. Фактори прийняття рішення (Decision Drivers)

Основними факторами вибору архітектури є:

1. Простота розробки та підтримки проєкту.
2. Низька зв'язаність між доменними модулями.
3. Можливість незалежного розвитку окремих частин системи.
4. Забезпечення цілісності даних під час конкурентних операцій.
5. Можливість масштабування системи в майбутньому.
6. Відсутність надмірної складності інфраструктури на початковому етапі.

## 3. Розглянуті варіанти (Considered Options)

### Варіант 1. Мікросервісна архітектура (Microservices)

Переваги:
- Незалежне розгортання окремих сервісів.
- Можливість окремого масштабування компонентів.
- Ізоляція окремих доменних областей.

Недоліки:
- Складніша інфраструктура.
- Необхідність міжсервісної комунікації.
- Додаткова складність забезпечення цілісності даних.

### Варіант 2. Класичний моноліт (Classic Monolith)

Переваги:
- Простота розробки та розгортання.
- Єдина кодова база.
- Простота взаємодії компонентів.

Недоліки:
- Слабше розділення доменної логіки.
- Ризик виникнення тісних залежностей між компонентами.
- Складніше незалежно розвивати окремі частини системи.

### Варіант 3. Модульний моноліт (Modular Monolith)

Переваги:
- Єдиний процес розгортання.
- Чітке розділення доменних модулів.
- Контрольовані залежності між компонентами.
- Можливість подальшого виділення окремих модулів у сервіси.

Недоліки:
- Необхідність дотримання архітектурних меж.
- Потрібен контроль міжмодульних залежностей.

## 4. Прийняте рішення (Decision)

Обрано архітектуру **Modular Monolith (Модульний моноліт)**.

Система поділяється на чотири основні доменні модулі:

- `registration` — реєстрація користувачів та управління учасниками турнірів.
- `bracket` — побудова турнірних сіток.
- `match` — управління матчами та їхніми результатами.
- `rules-engine` — перевірка правил настільного тенісу.

Кожен модуль має власну відповідальність та публічний інтерфейс взаємодії.

Міжмодульна комунікація здійснюється через Facade та DTO. Залежності передаються через Dependency Injection.

## 5. Стек технологій (Technology Stack)

### 5.1. Core & Runtime

- **Node.js (LTS) та TypeScript** — середовище виконання та статична типізація.
- **Fastify** — HTTP-фреймворк для побудови API.

### 5.2. Валідація та база даних

- **Zod** — перевірка вхідних даних.
- **PostgreSQL** — реляційна база даних із підтримкою транзакцій.
- **Prisma ORM** — взаємодія з базою даних та управління схемою.

### 5.3. Тестування

- **Vitest** — передбачений інструмент для модульного та інтеграційного тестування.
- **Playwright** — передбачений інструмент для E2E-тестування.

## 6. Ключові технічні рішення (Key Architectural Decisions)

### 6.1. Захист від конкурентного доступу (Race Conditions)

Під час одночасної реєстрації декількох користувачів на останнє вільне місце турніру може виникнути перевищення допустимої кількості учасників.

Рішення:

- Використання транзакцій бази даних.
- Блокування запису турніру за допомогою `SELECT ... FOR UPDATE`.
- Перевірка умови `current_players < max_players`.
- Оновлення кількості учасників у межах тієї самої транзакції.

Якщо вільних місць немає, транзакція відкочується та повертається помилка `TournamentFullException`.

### 6.2. Механізм ідемпотентності (Idempotency Key)

Для захисту від повторної обробки запитів передбачено заголовок `X-Idempotency-Key`.

Для збереження інформації про запити використовується таблиця `IdempotencyKeys`.

Кожен запис пов'язаний із конкретним користувачем та матчем через `user_id` і `match_id`.

Алгоритм роботи:

1. Сервер отримує запит із ключем ідемпотентності.
2. Перевіряє наявність відповідного ключа.
3. Якщо ключ має статус `COMPLETED`, повертається раніше збережена відповідь.
4. Якщо ключ новий, створюється запис зі статусом `IN_PROGRESS`.
5. Після успішної обробки запиту результат зберігається, а статус змінюється на `COMPLETED`.

Збереження результату матчу та завершення обробки ключа повинні бути узгоджені транзакційно.

## 7. Наслідки рішення (Consequences)

Позитивні наслідки:
- Чітке розділення відповідальності між модулями.
- Спрощення підтримки та тестування системи.
- Контроль міжмодульних залежностей.
- Можливість подальшого розвитку архітектури.

Негативні наслідки:
- Потрібно контролювати дотримання меж модулів.
- Необхідно підтримувати спільні правила взаємодії.
- Потрібно додатково перевіряти відсутність циклічних залежностей.
